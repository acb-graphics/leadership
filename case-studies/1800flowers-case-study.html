1-800-Flowers wanted customers to be able to find and send a gift by talking — no app, no screen, no browsing. At the time, Amazon Pay's voice-purchase path wasn't documented, and completing an end-to-end transaction in-skill was largely untested territory.

01

Overview

I owned conversational design, flow architecture, and the research protocol. Because there was nothing visual to hand off, my output was the engineering specification — which meant the responsibility ran further down the build than it normally would.

Every branch that wasn't resolved in the flow was a branch nobody would resolve at all. That forced a different kind of rigor: a layout can hold ambiguity; a sentence cannot.

Scope and methods

  • Scope. 4 core scenarios architected to command level, ~30 flow nodes, 8 test participants, one utterance library delivered to the client.
  • Methods. Conversational flow architecture, Wizard-of-Oz utterance testing, affinity mapping, emotional and tonal session coding.
  • Tools. Figma for flow mapping, spreadsheets for utterance documentation, Zoom for simulated sessions.
02

Problem

Take someone from "order flowers for my mom's birthday" to a completed, paid order — using only speech.

Voice commerce was an open category at the time. Completing a purchase inside a skill, rather than handing off to a phone or browser, was the strategic differentiator. The constraint — no visual interface — could become an advantage if the conversation carried the entire transaction, because gifting is time-pressured and often done badly under that pressure.

Why it had stalled

  • Amazon Pay's voice path wasn't documented. The payment flow didn't appear in the public Alexa developer guide, so the constraints governing the entire checkout were unknown before the project started.
  • No screen meant no fallback. Every edge case — a mishearing, a wrong address, an abandoned order — had to be resolved in language. There was no layout to absorb ambiguity.
  • Design had to serve as engineering spec. With nothing visual to hand off, the flows themselves became the build documentation. That raised the bar on precision far past normal design fidelity.
03

Research

I built the test rig before the product existed. Eight participants tested the utterance set via Zoom; I voiced Alexa live while they spoke naturally. Phrases like "send the same as last time" only surface in actual conversation with a device.

What the research showed

  • Reorder had to be offered, not requested. Testing showed people didn't spontaneously ask for it — it became a core interaction pattern.
  • Floristry knowledge isn't a given. Participants couldn't picture species and colors from description alone, a structural constraint voice cannot solve.
  • Occasion-based recommendation anchors the flow. Leading with "Who and what's the occasion?" set up the rest of the conversation.
04

Process

  1. 01

    Mapped Amazon Pay's undocumented voice-purchase constraints. Direct working sessions with Amazon's team revealed the payment flow's branch points and fallback paths — knowledge that didn't exist in public documentation at the time.

  2. 02

    Built the Wizard-of-Oz test rig. Structured the utterance testing so I could voice Alexa live while participants spoke naturally, capturing real language patterns in a transcript that became the flow architecture.

  3. 03

    Converted test transcripts into flows. Affinity mapped the testing notes into conversation branches, then specified each branch to the level an engineer could build from. Coded sessions by emotional tone to identify where flows felt natural versus forced.

05

Solution

A skill that carries a gift purchase from intent to paid order without a screen, specified precisely enough that engineers built from the flows alone.

Occasion-based recommendation opens the conversation. Reorder is offered rather than requested, because testing showed people didn't know to ask. Arrangement and size are confirmed in sequence with price stated first. The Amazon Pay handoff completes the transaction in-skill, with address and payment fallbacks handled entirely in language.

What was delivered

  • Conversational flows. Four core scenarios (new user, returning user, browsing, purchase) architected to individual spoken commands.
  • Amazon Pay constraints mapped. A working understanding of the voice-purchase flow's branch points and fallbacks, established through direct partnership rather than documentation.
  • Utterance library. A structured reference grounded in how real people speak, built to extend. This became the artifact the client continued to use.
06

Impact

The skill shipped as one of the earliest Alexa skills to complete a purchase end to end through Amazon Pay. The client used the flows and utterance library as the foundation for the production system.

Subsequent reporting indicated positive user response with increasing repeat purchases. No completion rates or order volumes were instrumented, but the utterance library became a durable asset the client continued to extend independently.

What it delivered

  • Design documentation that functioned as engineering spec, removing the translation layer between design and build.
  • A reference library for voice interactions that the client owned and could maintain independently.

What I'd do differently

I'd run a second, larger utterance testing round before launch. In voice, the failures live in the long tail. I'd also fix measurement at the start of the engagement — the work shipped, but I can't point to commercial outcomes.

What I learned

Designing without a screen exposed how much visual interfaces let you defer decisions. A layout can hold ambiguity; a sentence cannot. That permanently changed how I think about edge cases in any medium.
